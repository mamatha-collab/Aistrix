# Agents on AEX, phase A (November 11, 2026)

An **Agent** is now a first-class platform resource: a versioned spec with its own runtime. It is released, promoted through environments, gated by evals and run through the same AEX orchestrator as Applications.

The legacy `agent` app type (prompt plus an "autonomous mode" instruction and an in-memory tool loop in `main.py`) is unchanged. It still runs as before, and the Agents tile in Dev Studio still creates that app type. **No UI was added.** The API below is ready for screens to be designed on.

## What a developer writes

An Agent spec, YAML or JSON. Example: [examples/support-agent](../../examples/support-agent/aistrix.yaml).

| Field | Meaning |
|---|---|
| `spec.model` | `policy:fast/balanced/best` or `claude/…`, `openai/…`, `gemini/…`, same as pipeline nodes. |
| `spec.instructions` | System prompt, up to 20,000 characters. |
| `spec.input` | JSON Schema for the run input. Default: `{message: string}`. |
| `spec.output` | Optional JSON Schema. When set, the final answer must be JSON that matches it (one repair turn is allowed). Without it, the answer is text. |
| `spec.tools[]` | `name`, `description` and `parameters` (an object JSON Schema), plus either `http` (`method`, `url`, `headers`, `body`) or `code` (a deployed Code Application id). |
| `spec.tools[].approval` | `auto` (default): writes (POST/PUT/PATCH/DELETE) wait for a person. `always`: every call waits. `never`: writes run unattended. |
| `spec.limits` | `maxSteps` (model turns, default 10, max 50), `maxToolCalls` (default 20, max 100), `timeoutSeconds` (default 300, max 900). |
| `policies` | Same as Applications: `secrets`, `outboundHosts`, `budget.perRunUsd` (default $1), `providers`, `maxConcurrentRuns`. |
| `tests` | EvalSuite refs that must pass before production. |

Compile-time checks:
- Tool URLs must use a written-out host listed in `outboundHosts`, or a test destination.
- Templates may read only `{{args.<parameter>}}` and `{{secrets.<NAME>}}`.
- Secrets may appear only in the URL or headers, and only if declared.
- The model's provider must be allowed by `policies.providers`.
- Tool names must be unique, and `parameters` must be an object schema.

## How it runs

An Agent compiles to a one-step plan: `agent.loop`, implemented in [aistrix_platform/agent.py](../../aistrix-backend/aistrix_platform/agent.py).

- **Model calls** go through the model gateway's new `converse` turn. It applies the same run budget, owner key and spend reservation and settlement as other model calls. Claude uses the Messages API with tools; OpenAI and Gemini use Chat Completions tools. The same code serves hosted and local runs (`gateway.sdk_chat`).
- **Durable progress.** The conversation is saved on the step after every model turn and every tool result. A crashed or retried run continues from there: a paid model turn is never repeated, and a finished tool call is never run again.
- **Writes.** A write is marked dispatched before it is sent. It carries an `Idempotency-Key` derived from the run, step and tool call, so resending it after a crash is safe.
- **Approvals.** A call that needs approval pauses the run as `waiting_approval`, with `pending = {tool, arguments, callId, description, writes}`. Approving runs the call. Rejecting sends "A reviewer rejected this call" plus the note back to the model, which can change course. Eval runs and the local runner's `--approve`/`--reject` decide automatically.
- **Tool problems the model can fix** are returned to it as tool errors and the run continues. These are: an unknown tool, invalid arguments, a 4xx response from the API, a missing optional argument, and a failed code job.
- **Configuration problems fail the run**, for example a secret with no value. Transient failures (timeouts, 429, 5xx) retry the step from its saved progress, up to 3 attempts.
- **Limits** fail the run with a clear error: the model-turn limit, the tool-call limit, the run budget and the step timeout.

## API (for Studio, SDK, CLI)

The existing platform endpoints all accept Agents: validate, plan, releases, environments (promote and rollback), secrets, evals and release detail with the gate.

| Call | Purpose |
|---|---|
| `POST /v1/platform/agents/{ns}/{name}/runs` | Body `{input, environment?, version?, wait?}`. With `wait: true`, returns the finished or waiting run. With `Accept: text/event-stream`, streams events. Without either, returns 202. |
| `GET /v1/platform/runs/{id}` | The run. `steps.agent.state.messages` is the conversation; `steps.agent.state.calls` is each tool call's status and result; `steps.agent.detail` has `turns`, `toolCalls`, `costUsd`, `provider` and `model`. |
| `GET /v1/platform/runs/{id}/events` | The trace: `agent.turn` (text, tool calls, usage, cost), `agent.tool` (tool, status, result), `agent.waiting`, `agent.approval`, `agent.repair`, plus the usual `run.*` and `node.*` events. |
| `POST /v1/platform/runs/{id}/approvals/agent` | `{approved, note?, wait?}` approves or rejects the pending tool call. |
| `GET /v1/platform/releases/{id}` | `evaluation.workloads[0].external_steps` lists the write tools that eval suites must mock; `gate` is the production eval gate. |

SDK: `client.ask("ns/name", "message")`, `client.ask_stream(...)` and `client.approve(run_id, "agent")`. CLI: `aistrix ask ns/name "message" [--env staging] [--stream]`. Local runner: `python -m aistrix_platform.local agent.yaml -i '{"message": "..."}'`.

Eval suites target `Agent/ns/name@version` with `workload: agent`. Write tools are mocked by tool name, and a suite that leaves one unmocked is refused before anything runs.

## Verification

- `tests/test_platform_agent.py` has 34 tests with a scripted model, a fake API and the in-memory store. They cover:
  - spec and compiler checks
  - tools with arguments and secrets, and secrets kept out of the trace and state
  - approval, rejection, `never`/`always`, and automatic approval
  - a worker crash mid-write: resumed with no repeated model turn and the same idempotency key, applied once
  - unknown tools and bad arguments, API errors and retries
  - the turn, tool-call and budget limits, and structured answers with repair
  - provider message formats, reused tool-call ids, missing secrets
  - releases, the production gate and evals with mocks, and the example spec
- `tests/checks/check_platform_api.py` runs end to end through `main.py`, with Supabase, the Anthropic SDK client and outbound HTTP faked. It covers:
  - plan, release and promote, secrets, run, approve, the trace and ownership
  - the Claude `tool_use` and `tool_result` shapes the real adapter sends
  - cost per turn, no secrets in records, SDK `ask` and CLI `aistrix ask`

  It passes with the AEX flags off and on.
- **Not yet verified:** a real model on staging. The next step is the same procedure as the native prompt and structured rollouts: staging with the owner's own Claude key, the example agent pointed at a test destination, and an eval run.

## Not in phase A

- **Sessions and memory.** Each run is one conversation; there are no threads across runs and no long-term memory.
- **Tools.** No MCP client or hosting, no tool catalog shared with Workflows, no OAuth connections per end user, and no agent-as-tool or multi-agent handoffs.
- **Tests and channels.** No trajectory checks in eval suites (only output checks), and no chat widget or Slack/Teams channels.
- **Dev Studio screens** for creating, testing, tracing and approving.
- **Moving the legacy `agent` app type** onto this runtime, with a parity report as was done for prompt and structured.
