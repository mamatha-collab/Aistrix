# Aistrix status — November 10, 2026

## Assessment

Aistrix has a working local application platform and an early composable execution platform. It is not yet the complete architecture described in the adopted revision. The developer chooser is implemented, but its thirteen categories describe capabilities with different levels of completion; they are not thirteen finished product studios.

This audit inspected the adopted DOCX, current source, implementation notes, Git status, local service health, linked staging migrations and E2B account access. Remote checks were read-only. No workers were restarted, migrations applied, production changes made, model calls issued or E2B sandboxes created during this audit.

`aistrix_platform/spec.py` explicitly implements only Application, EvalSuite, Dataset, SecretRef and Environment, and only pipeline Application workloads. Other envelope kinds being recognized is not implementation of those resources. ## Current operational findings

1. The local frontend responds on port 3000 and the API health check returns HTTP 200 on port 8001.
2. E2B read-only authentication/template preflight succeeds. Account inventory returned zero active sandboxes. Configuration selects E2B, enables code execution and sets a shared 3,600-second daily reserved-runtime allowance.
3. No local `e2b_worker.py` process was present. Stored build/run worker heartbeats last updated November 2, 2026. Their entries cannot satisfy the 90-second health requirement, so builds/previews require the coordinator to be started. Its previous log contains generic queue-storage-unavailable messages; the underlying historical failure was not diagnosed by those messages.
4. Linked staging project `qhfxnpsvdolaftaljvdp` has all 48 local migrations recorded, including Studio, E2B routing and the persistent runtime ledger. Frontend and backend staging projects match through the supported legacy public-variable alias.
5. Staging configuration leaves `AEX_WORKFLOWS`, `AEX_APP_TYPES` and `AEX_NATIVE_TYPES` off/unset. Historical opt-in verification does not mean those paths are now enabled for ordinary staging traffic. The local API launcher disables lifespan/background sweeps, so its health response does not establish automatic recovery or schedule processing.
6. The working tree contains substantial modified and untracked implementation files. No reviewed commit/PR or remote frontend/backend deployment of that entire working tree was established by this audit. Applied database migrations alone do not deploy application code.
7. Older `implementation-plan.md`, `gap-analysis.md` and `current-state.md` are October 24 snapshots and conflict with later decisions in places. In particular, the adopted October 27 architecture retains Python/FastAPI and requires measured justification before introducing Go. The old Go roadmap is not the current implementation requirement.

## Recommended order

1. Restore and supervise the E2B coordinator; diagnose storage failures, add actionable health reporting, then repeat a small real signed-in Studio journey.
2. Consolidate and review the current changes, align the roadmap with the adopted architecture, and deploy frontend/backend together to staging.
3. Complete one shared-contract pipeline plus minimal stateful Agent demonstration, including approval/restart, sandbox validation, controlled external write reconciliation, evaluation gate and SDK/CLI/Studio agreement.
4. Verify hosted authentication/tenant denial, failure recovery, rollback, retention and measured costs/load before claiming production readiness or capacity.
5. Expand reusable Node/Tool authoring next; add custom dependency templates, Knowledge Base and MCP capabilities in separately testable increments.
